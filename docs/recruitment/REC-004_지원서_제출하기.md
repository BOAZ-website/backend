# 지원서 제출하기

| 항목 | 내용 |
|------|------|
| ID | REC-004 |
| HTTP Method | POST |
| Domain | Recruitment |
| 화면 | User |
| 상태 | 완료 |
| 우선순위 | P1 |
| Notion URL | - |

> ⚠️ **변경 이력:** User OAuth 로그인 도입에 따라 기존 비인증 API를 수정. 인증 추가, URL 구조 변경, 중복 제출 방지 로직 추가.

---

## 📝 개요

로그인한 사용자가 모집 기간 내에 지원서를 최종 제출한다.
`applicants` 테이블에 지원자 정보를 저장하고, `applicant_answer` 테이블에 질문별 답변을 저장한다.
기존에 임시저장(DRAFT) 상태의 지원서가 있는 경우 해당 레코드를 업데이트하고 `SUBMITTED`로 전환한다.

---

## 📐 비즈니스 규칙

- [ ] 로그인한 사용자만 지원서를 제출할 수 있다.
- [ ] 모집 기간(start_date ~ end_date) 내에만 제출할 수 있다.
- [ ] 해당 모집 공고에 이미 `SUBMITTED` 상태의 지원서가 있으면 재제출할 수 없다.
- [ ] 해당 모집 공고에 `DRAFT` 상태의 지원서가 있으면 해당 레코드를 업데이트하고 `SUBMITTED`로 전환한다.
- [ ] 동일한 `(recruitment_id, user_id)` 조합은 하나의 지원서만 허용한다.
- [ ] 지원 부문(track)은 `ANALYSIS`, `VISUALIZATION`, `ENGINEERING` 중 하나여야 한다.
- [ ] 모든 필수 질문에 대한 답변이 포함되어야 한다.
- [ ] TABLE 단일선택(`metadata.multiple` 없거나 `false`) 답변: 각 행의 값은 문자열 1개여야 한다.
- [ ] TABLE 복수선택(`metadata.multiple: true`) 답변: 각 행의 값은 문자열 배열이어야 하며, 필수 질문의 경우 최소 한 행에서 하나 이상 선택되어야 한다. 같은 행에 중복된 시간이 포함된 경우 서버에서 dedupe 후 저장한다.
- [ ] 이메일 형식이 올바르지 않은 경우 400을 반환한다.
- [ ] 전화번호는 하이픈 없이 숫자만, 10~11자리여야 한다.
- [ ] 생년월일은 `YYYY-MM-DD` 형식이어야 한다.

## ⚠️ 예외 처리

| 데이터베이스/서버 내부 오류 | 500 | `INTERNAL_SERVER_ERROR` | 서버 내부 오류가 발생했습니다. |

## 🔌 API 스펙

> 협의 상태: ⚪ 미협의

**Request**

```
POST /api/v1/recruitment/{recruitmentId}/applications
```

| 파라미터 | 위치 | 타입 | 필수 | 설명 |
|---------|------|------|------|------|
| Authorization | Header | STRING | ✅ | `Bearer {userAccessToken}` |
| recruitmentId | Path | LONG | ✅ | 지원할 모집 공고 ID |
| track | Body | STRING | ✅ | 지원 부문 (ENUM: `ANALYSIS`, `VISUALIZATION`, `ENGINEERING`) |
| name | Body | STRING | ✅ | 성명 |
| email | Body | STRING | ✅ | 이메일 |
| phone | Body | STRING | ✅ | 전화번호 (하이픈 없이 숫자만, 10~11자리) |
| university | Body | STRING | ✅ | 대학교 |
| major | Body | STRING | ✅ | 본전공 |
| minor_double_major | Body | ARRAY | ❌ | 부전공/복수전공 목록 |
| last_semester | Body | INT | ✅ | 마지막 재학 학기 |
| military_status | Body | STRING | ✅ | 병역 상태 (ENUM: `COMPLETED_OR_EXEMPT`, `NOT_COMPLETED`) |
| birth_date | Body | STRING | ✅ | 생년월일 (`YYYY-MM-DD`) |
| graduation_date | Body | STRING | ✅ | 졸업 예정 시점 (예: `2026-02`) |
| grad_school_plan | Body | BOOLEAN | ✅ | 대학원 진학 여부 |
| answers | Body | ARRAY | ✅ | 지원서 답변 목록 |
| answers[].question_id | Body | LONG | ✅ | 질문 ID |
| answers[].answer | Body | ANY | ✅ | 답변 (TEXT: 문자열, TABLE 단일선택: `{"행":"열"}`, TABLE 복수선택: `{"행":["열1","열2"]}`) |

**Response (201 Created)**

```json
{
  "status": 201,
  "data": {
    "applicant_id": 42,
    "submitted_at": "2026-08-10T14:30:00"
  }
}
```

**Response (409 Conflict — 이미 제출됨)**

```json
{
  "status": 409,
  "error_code": "ALREADY_SUBMITTED",
  "message": "이미 제출된 지원서가 있습니다."
}
```

**Response (409 Conflict — 모집 마감)**

```json
{
  "status": 409,
  "error_code": "RECRUITMENT_CLOSED",
  "message": "모집이 마감되었습니다."
}
```

**협의 포인트**

- [ ] DRAFT 상태에서 제출 시 기존 레코드를 update할지, 삭제 후 신규 생성할지 (현재: update)
- [ ] 제출 완료 후 응답으로 `applicant_id` + `submitted_at`만 반환할지, 지원서 전체 데이터를 반환할지

## 🧠 의사결정 이력

| 날짜 | 고민했던 선택지 | 최종 결정 | 결정 이유 |
|------|---------------|-----------|-----------|
| 2026-05-16 | 이메일 기반 중복 체크 vs `(recruitment_id, user_id)` UNIQUE 제약 | `(recruitment_id, user_id)` UNIQUE 제약 | 로그인 필수화로 user_id가 확보되므로 이메일 기반 중복 제거 로직 불필요. DB 레벨에서 보장하는 것이 안전 |
| 2026-05-16 | `recruitment_id` body 수신 vs path parameter | path parameter | RESTful 구조에 맞고 URL만으로 리소스를 특정할 수 있어 일관성 향상 |
| 2026-05-16 | DRAFT 존재 시 별도 에러 반환 vs SUBMITTED로 전환 | SUBMITTED로 전환 | 임시저장 후 그대로 제출하는 흐름을 지원하여 UX 향상 |
| 2026-06-04 | TABLE 복수선택 구분 방법 (별도 Type vs metadata 플래그) | `metadata.multiple` 플래그 | 기존 데이터 호환 유지, QuestionResponse 패스스루로 프론트 전달 공짜 |
| 2026-06-04 | 복수선택 중복 원소 처리 (400 거부 vs dedupe 저장) | dedupe 후 저장 | 프론트 체크박스 UI에서는 중복이 발생하지 않으므로, 비정상 요청에 대해 관대하게 정규화 |

## 📎 비고

- User 전용 API로, 요청 헤더에 유효한 User AccessToken(`Authorization: Bearer {token}`)이 포함되어야 한다.
- `user_id`는 요청 바디로 받지 않으며, JWT 토큰에서 서버가 직접 추출한다.
- 현재 DB 제약상 `applicants.user_id`가 UNIQUE이므로(엔티티 `@OneToOne`), 한 유저는 전체 기수를 통틀어 지원서를 1건만 가질 수 있다. (명세상 `(recruitment_id, user_id)` 조합보다 강한 제약 — 단일 기수 운영 기준)
